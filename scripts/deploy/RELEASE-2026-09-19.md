## 2. The order, and the one place it is load-bearing

```
2.1 migration 0009  ──►  2.2 migration 0010  ──►  2.3 image  ──►  2.4 first trade walk  ──►  2.5 verify
```

**Migrations before the image, and both before the walk.** `0009` creates
`trade_readings` and widens `runs.kind` to admit `trades`; `0010` lets a second walk
of the same day land when it is deeper. An image carrying `keel trades` against a
schema without `trade_readings` fails on the first insert, after it has already
spent Horizon requests against the NFR-6 budget.

Neither migration is in the running deployment: both landed on 19 September, after
`e467a35` was built.

### 2.1 / 2.2 The schema

Runbook section 3.5 is the procedure and it is unchanged. From the checkout on the
box, with `KEEL_MIGRATE_DSN` set as that section describes:

```bash
cd "$KEEL_DIR"
git fetch --all --tags && git checkout ddab9ac
scripts/migrate.sh
```

`scripts/migrate.sh` applies what is outstanding in order, so `0009` and `0010`
need no separate invocation. **Read its output rather than its exit code**: it names
each file it applies, and a run that applies nothing is the symptom of a checkout
that did not move.

### 2.3 The image

The deploy job is gated on the repository variable `KEEL_DEPLOY_TARGET`, which is
already set, and fires on a `v*` tag or on `workflow_dispatch`. Tagging is Al's:

```bash
git tag -a v0.9.0 -m "trade-derived metrics: FR-9 and FR-10 reach the API"
git push origin v0.9.0
```

Then set `KEEL_IMAGE_TAG` in `.env` on the box to the SHA the workflow published and
bring the stack up, per runbook section 3.7.

**`docker-compose.prod.yml` already carries the service that fills the cache.**
`keel-trades` runs `trades -interval 24h` at line 375, beside `keel-holders` at 302
and `keel-scan` at 251. Nothing needs adding to the compose file; it shipped with
the feature, which is section 3.6b's whole point.

### 2.4 The first walk, by hand, once

The 24-hour service will not fill an empty cache quickly enough to see, so the first
pass is started deliberately. Runbook section 3.6b:

```bash
cd "$KEEL_DIR"
docker compose -f docker-compose.prod.yml run --rm keel-serve trades
```

**About 23 minutes** for the 39 pairs under the DEC-019 threshold. Use `tmux` or
`screen`: an SSH drop kills a `docker compose run` and wastes the walk, which is the
same warning section 3.9 carries for replay.

**Two outcomes that read like failures and are not**, both from section 3.6b:

- `last-genuine-only ... above the DEC-019 threshold of 20000 trades in 30 days`.
  That pair is one of the 21 the accepted option deliberately does not walk in full.
- A pair that stops on the 400-page bound. `keel trades -max-pages` defaults to 400
  and 4 of 64 pairs hit it. Those rows are stored with `page_cap` named in the reason
  string, and FR-10 stays **genuinely unevaluated** for them. That is the honest
  answer and not a gap to close by raising the cap.

## 4. The one finding this release surfaced and does not fix

**The methodology version set is split three ways, not two.** DEC-014 decided, on
5 September 2026, that the version in force is ONE number for the whole set. Today:

| What | Version |
|---|---|
| `01-data-sources.md`, `11-limitations.md` | **1.2.0**, and not `-draft` |
| the other eleven methodology files and `README.md` | **1.1.0-draft** |
| `internal/domain.MethodologyVersion`, and the contract's examples | **1.0.8-draft** |

`docs/internal/deliverable-and-week-trackers.md` recorded this as a two-way split.
It is three, and two files have dropped the `-draft` suffix, which is a stronger
claim than any of the others make.

This is not fixed here for two reasons and both are zone rules. `docs/methodology/`
is RED: Al writes what a version header asserts. And DEC-014 is a decision, so
re-deciding the number in force is Al's even though the bookkeeping that follows is
Claude's. `docs/decisions/DEC-014-methodology-version-unified.md` now carries a
drafted amendment stating the measured state and the two roads; it decides nothing.

**It does not block this release.** The API serves `methodologyVersion: 1.0.8-draft`
and that string is CORRECT: it is what the code that computed the row was stamped
with. What is wrong is that a reader comparing the served version against the
documents finds three answers.
