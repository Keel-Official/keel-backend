# Evidence: which asset an order book level's `amount` is denominated in
#
# Collected 24 August 2026 from Horizon mainnet. Every command is free, needs no
# account, and can be re-run by anyone. It answers a question internal/horizon
# had to answer before it could put a bid into a domain.Level, because
# domain.Level.Amount is defined in BASE units and docs/methodology/04-depth.md
# section 1 computes depth as price times amount.
#
# THE ANSWER: the two sides are NOT denominated in the same asset.
#   asks -> amount is in the BASE asset,  price_r as the offer posted it
#   bids -> amount is in the QUOTE asset, price_r INVERTED from the offer
#
# The method, and it is the reason this is evidence rather than an opinion: an
# entry on /offers has no ambiguity at all, because an offer's amount is the
# amount of the asset it SELLS. So each side of /order_book is matched against
# the offers behind it. A bid is an offer selling the quote asset; an ask is an
# offer selling the base asset.

# ------------------------------------------------------------ the comparison
#
# Take the bid level at price 1.0721777 with amount 100.0000000. The offer list
# holds amount=100.0000000 at price 0.9326812, price_r 10000000/10721777. Same
# amount to the last digit, and the price is the exact reciprocal: the book
# reports 10721777/10000000. Horizon inverted the PRICE into quote-per-base and
# left the AMOUNT in the asset the offer sells, which is USDC.
#
# Every other bid level pairs the same way: 5464.4640894 at 1.0725038 against
# the offer 5464.4640894 at 428369451/459427867, 52456.1449581 at 1.0722137
# against 498425963/534419142, 216178.3600767 at 1.0711948, 450.0000000 at
# 1.0711585, 61.4870392 at 1.0600000.
#
# Now the ask side. The book's 1.1684309 at 106.7372828 appears in the offer
# list as amount=1.1684309 at price 106.7372828, price_r 266843207/2500000, NOT
# inverted. Same for 99.9999962 at 77.0584670, 113.5163207 at 400.0584670,
# 88.5084729 at 1.0900000, 87.4930682 at 1.1300000, 0.0100677 at 2.0000000, and
# 47700.2581949 at 1.0732864.
#
# So internal/horizon converts a bid with amountBase = amount × d / n and leaves
# an ask alone. The multiplication is exact and only the final division rounds.
# The notional recovers Horizon's original quote amount, which is the invariant
# TestBidAmountUnitConversion asserts.
#
# WHY IT MATTERS, in the one number that shows it. A bid of 216178.3600767 read
# as base units yields a notional of 231,569.14 USDC. Read correctly it yields
# 216,178. Reading the bid side as base overstates sell-side depth by the price
# factor, and sell-side depth is the liquidation term of C_max in
# docs/methodology/08-collateral.md. The error inflates the collateral a lender
# is told is safe.

# --------------------------------- 3. not every endpoint sends Latest-Ledger
#
# Found by running the recorder against live Horizon, not by reading docs. The
# first version required the header on every response and failed on its first
# real request. The collection endpoints send it; the single ledger resource
# does not, and does not need to, because it carries its own sequence.

$ for u in "ledgers/64091851" "liquidity_pools?reserves=USTRY:$USTRY_I,USDC:$USDC_I" "assets?asset_code=USTRY"; do
    curl -s -o /dev/null -D - "https://horizon.stellar.org/$u" | grep -iE "^(HTTP|Latest-Ledger)"
  done
